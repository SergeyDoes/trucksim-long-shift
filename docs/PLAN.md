# Long Shift — план для Claude Code

(до переименования — Fatigue Drift; начинался в монорепозитории ATS-Mods, 2026‑10‑25 вынесен в отдельный репозиторий trucksim-long-shift. Спайк этапа 1 лежит в `docs/spike/` и больше не собирается.)

Плагин для American Truck Simulator (и ETS2): когда водитель устал, руль начинает медленно уводить в сторону. Штатное затемнение экрана при этом не трогаем. Основа — официальный SCS Telemetry SDK: C++, Windows x64, DLL‑плагин.

> Для Claude Code: ничего не коммить и не пушить, коммиты я делаю сам. После каждого этапа останавливайся и показывай результат.

---

## 0. Контекст и допущения (проверить в первую очередь)

- SDK: SCS Telemetry SDK 1.14 с Input API (`scssdk_input.h`), официальный архив `https://download.eurotrucksimulator2.com/scs_sdk_1_14.zip` (ссылка с modding.scssoft.com). Лежит в `third_party/scs_sdk/` вместе с его лицензией (MIT‑подобная). Зеркала не использовать.
- Плагины грузятся из `<ATS>/bin/win_x64/plugins/*.dll`. При первой загрузке игра показывает предупреждение о плагинах, это нормально.
- Признак усталости берём из канала телеметрии `SCS_TELEMETRY_CHANNEL_next_rest_stop` (`rest.stop`, s32, минуты до обязательного отдыха). Точное имя и тип проверь по заголовкам SDK.
- Работает только при включённой симуляции усталости в настройках игры.

Два главных неизвестных, от них зависит архитектура:
1. **Смешивание осей.** Если на Steering забинден и руль/геймпад, и виртуальное устройство плагина, суммирует ли игра их значения или берёт одно?
2. **Semantical‑устройство.** Может ли устройство типа `SCS_INPUT_DEVICE_TYPE_semantical` напрямую дёргать игровой контрол руления, минуя биндинг?

Предварительный ответ (по `scssdk_input_device.h` и `controls.sii` в текущих профилях ATS и ETS2):
`mix steering` = `dsteering - <ось руля/геймпада> - semantical.steering?0`. То есть semantical‑вход `steering` поддерживается, работает без биндинга и **суммируется** с клавиатурой и рулём; мёртвая зона и нелинейность руля к нему не применяются. В старых профилях (до ~1.38) `semantical.steering` в миксе нет. Спайк должен подтвердить это в игре.

## 1. Спайк: проверка Input API (до основного кода)

Цель — подтвердить в игре, что semantical‑вход `steering` складывается с рулём/клавиатурой, и снять цифры для модели.

- [x] CMake‑проект: DLL `fatigue_drift_spike.dll`, MSVC, x64, `/MT`, include из `third_party/scs_sdk/include` (код спайка теперь в `docs/spike/`).
- [x] Один DLL, два устройства:
  - semantical `fatigue_drift_sem`, вход `steering` (float) — основной вариант, без биндинга;
  - generic `fatigue_drift`, ось `steer_offset` (float) — запасной, нужен только если semantical не сработает.
- [x] Выход — синус с периодом ~4 с и амплитудой 0.3; semantical на паузе отдаёт 0.
- [x] Горячая клавиша Ctrl+Shift+F9 (только когда окно игры в фокусе) переключает режим: semantical → generic → off.
- [x] Телеметрия: `truck.input.steering`, `truck.effective.steering`, `truck.speed`, `rest.stop`, события `paused` / `started`.
- [x] Лог `long_shift.log` рядом с DLL: CSV 10 Гц (время, режим, наше смещение, input/effective steering, скорость, rest.stop, пауза, активность устройств) + ключевые события в игровую консоль через `common.log`.
- [x] Smoke‑тест вне игры: exe грузит DLL и прогоняет init / кадры / shutdown на заглушках API, дважды и в разном порядке.
- [x] Инструкция и чек‑лист ручного теста в `docs/spike/TESTING.md`.

По логу ответить:
- складывается ли наше смещение с рулём, клавиатурой и геймпадом;
- в какую сторону уводит положительное значение;
- попадает ли наше смещение в `truck.input.steering` (важно для детекта «пробуждения» на этапе 2);
- что делает FFB руля во время покачивания;
- что отдаёт `rest.stop` при выключенной усталости (и, если получится, после просрочки).

**Выход этапа:** таблица «вариант → работает / нет» + выводы по логу. По ней выбираем путь:
- semantical работает → **путь A** через semantical‑вход `steering` (этапы 2–4), без биндинга;
- semantical не работает, но generic‑ось складывается с рулём → путь A через generic‑ось с биндингом;
- ничего не складывается → **путь B** (внешняя программа с FFB на руле, этап 5) или путь A только для клавиатуры/геймпада.

### Результаты спайка (ATS 1.61.2, 2026‑09‑29)

| Вариант | Результат |
|---|---|
| semantical + геймпад | **работает**: смещение накладывается на руление геймпадом, биндинг не нужен |
| semantical, стоя, амплитуды 0.3 / 0.2 / 0.1 / 0.03 | работает, отклик линейный: размах `effective.steering` ≈ 0.64 × амплитуда, с запаздыванием ~1 с на стоянке |
| режим off | влияния нет |
| фризы | были из‑за пересчёта значения при каждом опросе; после расчёта раз в кадр телеметрии — нет (18–20 опросов за 0,1 с против 14 в off) |
| semantical + руль, FFB | **не проверено** — руля не было под рукой |
| semantical + клавиатура | не проверено |
| generic‑устройство | не понадобилось |

Выводы:
- Выбран **путь A через semantical‑вход `steering`**. Путь B и generic‑биндинг не нужны, если проверка с рулём не покажет обратного.
- Положительное значение уводит **вправо** (по часовой), отрицательное — влево.
- `truck.input.steering` при ненулевом semantical‑входе показывает только знак суммарного руления (ровно ±1), величина теряется. В 87 % строк он совпал со знаком нашего смещения, в 13 % был противоположным — игрок перекрывал смещение геймпадом.
- `rest.stop` идёт в игровых минутах и в городе убывает медленнее (масштаб времени), усталость в профиле включена.

## 2. Телеметрия и модель усталости (путь A)

- [x] `scs_telemetry_init`: подписаться на `rest.stop`, `truck.speed`, `truck.input.steering`, события `paused` / `started`. **Сделано в этапе 3**: каналы уже проверены спайком, а без input‑части подписка сама по себе ничего не даёт.
- [x] Модуль `FatigueModel` (`src/core/`), чистая логика без зависимостей от SDK:
  - вход: dt, `rest.stop`, скорость (м/с, как в `truck.speed`), `truck.input.steering`, пауза;
  - **множитель усталости** 0..1 по `rest.stop`: 0, пока до отдыха `start_minutes_before_rest` игровых минут и больше, линейно до 1 к `full_minutes_before_rest` (0 — отдых положен), после просрочки 1; без канала `rest.stop` — 0; равные значения — переключатель. Свой у зевков (по умолчанию 30 → 0) и у покачивания камеры (120 → 0).
  - выход: смещение руля, положительное — вправо, |смещение| ≤ `yawn.strength` × множители, не больше полного поворота;
  - случайность — `std::mt19937` с seed из конструктора.
- [x] Поведение дрейфа («микросон»):
  - зевки случайные (пуассоновский поток): в среднем раз в `average_interval_s` (30 с) от начала до начала, не чаще чем через `min_pause_s` (8 с) после конца предыдущего;
  - ~~слабый постоянный увод руля~~ — был (руль плавно гулял между случайными точками), пробовали 0.05–0.25 и медленный дрейф 0.06 / 8–20 с; **убран**: в жизни отпущенный руль сам выпрямляется, а сонливость — это отсутствие поправок, не болтанка. Осталось покачивание камеры (4а) и зевки.
  - **зевки** (сильный увод): сторона случайная; сила `yawn.strength × U(0.6..1)` (по умолчанию 0.25); плавный набор 2–4 с (smoothstep), удержание 2–5 с, плавный отпуск 1–2 с; в среднем раз в 30 с, пауза после зевка ≥ 10 с. Настоящий зевок игры («вы задремали») синхронизировать нельзя: SDK его не отдаёт (только `rest.stop`), в `game.log.txt` его тоже нет;
  - **множитель скорости** 0..1: скорость / `full_speed_mps`, дальше 1; на стоянке 0 (у камеры — `standing_strength`). Итоговая сила = `strength` × множитель скорости × множитель усталости;
  - «пробуждение» гасит только зевок: руление по `truck.input.steering` направлено против нашего суммарного смещения (у канала «влево» положительное, у нас «вправо», поэтому это одинаковый знак), и направление смещения задаёт зевок, а не фон — иначе игрок, компенсирующий фон, гасил бы зевок в другую сторону сразу при старте. Зевок гаснет экспоненциально (τ = 0.15 с), новый не раньше чем через 8 с;
  - на паузе зевок и фон сбрасываются, смещение 0; кадры длиннее 0.1 с обрезаются, чтобы не было скачков.
  - по игре (ATS 1.61, 2026‑09‑29): `rest.stop` после просрочки уходит в минус; стик геймпада в центре даёт `input.steering` = 0, «пробуждения» были реальными подруливаниями.
- [x] Unit‑тесты (`tests/`, doctest 2.4.11 через FetchContent): модель зевков, разбор ini, покачивание камеры — 36 сценариев. Проверено мутациями: 17 намеренных поломок (10 в модели, 7 в покачивании) ловятся тестами.

## 3. Сборка плагина (путь A)

- [x] Связать телеметрию → `FatigueModel` → ось input‑устройства (`src/plugin/plugin.cpp`, DLL `long_shift.dll`, semantical‑устройство `long_shift`, вход `steering`). Модель обновляется на `frame_end`, dt — по `paused_simulation_time`. Смещение считать в кадре телеметрии, а input‑callback только отдаёт готовое значение: игра сразу переопрашивает устройство, пока его значение меняется, и значение, пересчитанное от часов при каждом вызове, вешает главный поток (спайк: ~6 млн опросов/с и фризы по 1–2 с).
- [x] Всё состояние в одном объекте `Plugin`, глобален только указатель на него; объект живёт, пока инициализирован хотя бы один из API (telemetry / input), в любом порядке.
- [x] Защита: при любой ошибке инициализации плагин логирует и отдаёт 0 на оси, но не роняет игру (исключения не выходят из DLL; без телеметрии или без `rest.stop` устройство отдаёт 0).
- [x] Лог `long_shift.log` рядом с DLL (дописывается, обрезается после 1 МБ): инициализация, «отдых положен / нет», начало и конец эпизодов, пробуждение, пауза.
- [x] Smoke‑тест плагина (`tests/plugin_smoke.cpp`) на поддельном API игры: нет дрейфа до отдыха / без `rest.stop` / на стоянке, есть дрейф на 90 км/ч, ≤ 2 раундов опроса за кадр, пробуждение, пауза, отказ телеметрии → 0, лог.

## 4. Настройки и удобство

Значения по умолчанию — подобранные пользователем в игре. Если файла нет, плагин пишет его со значениями по умолчанию. Ошибки в файле — предупреждение в лог с номером строки, значение по умолчанию; понимает BOM, CRLF, десятичную запятую.
- [x] Debug‑режим: строка состояния раз в секунду (скорость, `rest.stop`, множители зевков и камеры, `input.steering`, фаза зевка, смещение, а также сколько микросекунд в секунду игра тратит в плагине и сколько раз опрашивает устройство), выключается `status_log = 0`.
- [x] Горячая перезагрузка ini: плагин раз в секунду проверяет время изменения файла и применяет новые значения на ходу — удобно подбирать силу увода без перезапуска игры.
- [x] README (на английском): что делает мод, требования, установка и удаление, все настройки ini, ограничения, диагностика, сборка из исходников. Совместимость с ETS2, рулём и клавиатурой заявлена как ожидаемая, но не проверенная.

- [x] Проверено в игре кивком на клавишах: `camud` двигает камеру, заметный сдвиг — около 10–20 единиц. Кивок по кнопке пользователю не подошёл; `lookblink` видимого эффекта не дал. Оба убраны.
- [x] Вместо этого — постоянное покачивание головы «смазанной» восьмёркой (`src/core/CameraSway.*`): влево‑вправо по синусу, вверх‑вниз с удвоенной частотой; скорость, размах и форма плавно случайно гуляют (`randomness`: 0 — чистая восьмёрка, 1 — сильно размыто). Сила — свой множитель усталости и скорости, меняется плавно (τ = 2 с), так что после отдыха голова мягко возвращается туда, куда смотрел игрок; на паузе камера замирает.
- [x] Плагин считает шаг раз в кадр отрисовки (повторные опросы того же кадра камеру не двигают) и отдаёт его через `camud` / `camlr`; если игра не примет эти входы — регистрируется только руль.
- [x] `[camera]` в ini: left_right, up_down, loop_time_s, randomness, standing_strength (доля покачивания на стоянке; дальше растёт со скоростью до полной к full_speed_mps), full_speed_mps, start/full_minutes_before_rest. Тесты: восьмёрка (2 волны вверх‑вниз на 1 влево‑вправо), шаги складываются в положение и возвращаются к 0, случайность смазывает петли и форму, пауза, без рывков, детерминизм; 7 намеренных поломок ловятся.
